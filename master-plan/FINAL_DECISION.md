## 2. Why DriftFix

1. **Most literal RFS fit.** The YC text describes the DriftFix demo almost word for word: scan customer codebases, find affected usages, open a PR.
2. **Proof the audience can check.** A real GitHub PR whose tests go from red to green. No other track has a result that judges can verify this easily.
3. **Judges have felt the pain.** Every engineer on the panel has been hit by a breaking API change.
4. **Runbook already done.** `BUILD_PLAN_DriftFix.md` has roles, checkpoints, fixtures and fallbacks, which is why its p_success is the highest of the six.
5. **Startup path.** A clear wedge buyer (API vendors), a data moat (a corpus of real migrations) and an obvious next step (a GitHub App).

**Where it is not best:** ScamShield scores higher on market urgency (9 vs 8) and equals it on demo impact. WarRoom matches it on technical depth. Neither gap comes close to closing the 0.79-point lead (see `scoring/RESULTS.md` §5).

## 3. How robust is the pick

- Across 20,000 runs with random weights and ±1 score noise, DriftFix finishes first 98.4% of the time and its mean rank is 1.02.
- **The one thing that could flip it is execution risk.** DriftFix loses first place only if its p_success drops below **0.62**. It is 0.80 now, and the master-plan change (LibCST codemods from the start) is aimed at exactly this number.
- Excluding every RFS-fit and judge-appeal advantage (setting R and J equal to ScamShield's) still leaves DriftFix ahead on feasibility-adjusted score: the remaining margin is +0.17 weighted and the p_success gap adds more.

## 4. Decision rules (when to switch)

| Trigger | When checked | Action |
|---|---|---|
| Phase 1 spike for DriftFix cannot produce a single verified fix in 45 minutes | Before the build starts | Re-score (F −2, p −0.20). If ScamShield then leads, switch |
| Team has no Python/backend strength but strong real-time voice/front-end | Before the build starts | Switch to ScamShield (its F and p rise for that team) |
| 3:30 PM checkpoint: no end-to-end fix | During the build | Do not switch projects. Apply the codemod-only fallback from the runbook |
| Organizers confirm a prize that only one track fits (e.g. a large on-device AI prize) | At check-in | Add +2 S to that track, re-run `score.py`, follow the result |

Switching projects after noon costs more than any score gap here, so after the build starts the only change allowed is the fallback within the project.

## 5. What the other five contribute

- **ScamShield:** the full backup plan, ready to build if a switch rule fires.
- **WarRoom:** a multiplayer DriftFix v2 where a team reviews and steers migrations together. It also backs the pitch answer "how do humans stay in control at fleet scale?"
- **RegDiff:** the same diff → impact → task → audit pattern, applied to regulations instead of API specs. It shows that the DriftFix engine generalizes.
- **DocSaathi, HumanPass:** post-event options; not competitive for an 8-hour build with this team.
